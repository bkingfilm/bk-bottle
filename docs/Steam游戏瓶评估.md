# 「在玩的 Steam 游戏」进漂流瓶——可行性评估

2026-08-10 · 评估稿；文末两项前置验证已于当日跑完，结论见第五节

**【08-10 晚更新】BK 拍板网页侧开工，worker + 网页侧当晚已上线**（版本 d2e7e92b，线上实测通过）：
- 网页扔瓶框直接贴 Steam 商店链接即可，预览、混装、卡片渲染全通
- 元数据走服务端验证（appdetails），失败自动回落客户端提供；假 appid 拒收且不烧额度
- 卡片按第四节第 3 条执行：封面 + 名字 +「TA 在玩」，点击跳 Steam，零促销元素
- 第四节第 2 条的三道反营销闸**未实装**：当前扔瓶量日均不足 1 条，巡查全覆盖，闸改为「同 appid 多设备重复出现即告警」的巡查规则，出现首例真实滥用或日新瓶量超巡查能力再补成代码（待 BK 拍板确认此取舍）
- 「🍾 装瓶」书签按钮同晚扩展支持 Steam：在自己的 Steam 资料页点书签，「最近活动」里的游戏自动填进扔瓶框（公开资料页不登录也能抓；老用户书签代码不会自动更新，需重新拖一次）
- 插件侧（库存页一键成瓶 + 商店页按钮）仍按计划留 0.1.7，等 0.1.6 过审后单独提交

## 结论

技术上能做，架构已经为它留好了口；但**当成「多一个能装的品类」做没有价值，当成「装瓶门槛的解法」做才有**。

现在的真问题是扔瓶人不涨：08-08 到 08-10 两天，捞瓶设备 +13，扔瓶设备 +1，插件装机 +15。装机涨了、来的人涨了、扔瓶没涨——说明缺的不是「能装什么」，是「装的动作太重」。加一个游戏品类，用户还是得手动挑、手动贴，门槛一点没降。

反过来，如果做成「读你 Steam 最近在玩的，一键成三个游戏的瓶子」，它就直接命中了这个瓶颈——那是这件事唯一值得做的形态。

## 一、架构上装不装得下

装得下，而且不用改地基。

现在的瓶子结构（`worker/src/index.js:367`）：

```
bottle = { id, device, videos: [ {vid,title,author} | {bvid,title,author} ], fans, fished, ts }
```

`videos` 数组本来就是异构的——YouTube 项带 `vid`，B站项带 `bvid`。加游戏就是第三种形态 `{appid, title, ...}`，`bottlePlatform()`（`index.js:290`）已经在按字段判平台，扩一个分支即可。

07-26 定的「不分池、一个瓶子里可以混装」在这里是顺风：游戏和视频混在同一片海，不需要新增池子、不需要捞瓶筛选。

## 二、元数据从哪来（这是真正的技术风险）

Steam 有个公开端点 `store.steampowered.com/api/appdetails?appids=<id>&filters=basic`，本机实测 200，返回 `name` / `header_image` / `type`，形态和 YouTube oEmbed 一样够用。

**但服务端调用这条路不能默认它通。** Steam 对该端点按 IP 限流（约 200 次 / 5 分钟），Cloudflare Workers 走的是共享出口 IP，撞限流甚至被直接拒的概率很高。这和 07-25 踩过的 B站 `-412` 是同一类坑：本机 curl 成功 ≠ Workers 机房成功。

好消息是那个坑已经趟出过路子：B站方案是**扔瓶人的浏览器提供元数据，服务端只做格式校验 + 封面域名白名单清洗**。Steam 直接复刻即可：

- appid 格式：纯数字，长度 ≤ 7
- 封面域名白名单：`shared.akamai.steamstatic.com` / `shared.cloudflare.steamstatic.com` / `cdn.akamai.steamstatic.com`
- 标题长度截断 + 现有 `SENSITIVE` 敏感词表照走

代价和 B站一样：客户端可以伪造标题，靠后台人工巡查兜底。

**上线前必须先验一件事**：部署一个测试 Worker 打 20 次 appdetails，看是不是全绿。通了就能做服务端验证（更抗伪造），不通就老老实实走客户端提供。别跳过这一步直接写实现。

## 三、「在玩的游戏」怎么读——三条路

### A. 插件读你自己的 Steam 库存页（推荐）

用户已登录 Steam 的前提下，`steamcommunity.com/my/games` 页面里有最近游玩列表和时长。插件**只在用户点击时**读当前页 DOM，挑 3 个，一键成瓶。

- 零 Steam API key、零 OpenID 登录、**不上传 steamid**，只上传 appid + 名字
- 完全落在现有商店申报口径里（「只在点击时读当前页 DOM，全部 fetch 只打自家 API」）
- 这是三条路里唯一真正降低装瓶门槛的

代价：加 `steamcommunity.com` host permission，要重新过审（Chrome 一般 1-3 天）。且只有插件用户吃得到——现在是 82 个。

### B. 插件在 Steam 商店页加「装进瓶子」按钮

和现在 YouTube / B站 播放页的机制完全一样，改动最小。但它降的是「贴链接」的门槛，不是「挑内容」的门槛，价值远小于 A。可以和 A 一起做，共用一个 host permission 申请。

### C. 网页端手贴 Steam 链接

无插件用户也能用，但门槛跟现在贴视频一模一样，没有任何改善。只适合作为兜底，不值得单独为它开工。

### 直接否掉的：Steam OpenID 登录

能拿到最完整的数据（`GetRecentlyPlayedGames` 全量 + 时长），但引入账号绑定，steamid 可反查真名、好友、购买历史。产品地基是「匿名 + 真实消费记录」，07-25 已经定过「不可动」。这条路不走。

## 四、产品层面的三个真问题

**1. 捞到游戏 ≠ 能立刻消费。** 视频点开就看，这是「捞一下」这个动作成立的前提。游戏是几十块钱加几十小时的决定，捞到一张游戏卡片，用户当下什么也做不了。

~~对策：单瓶游戏数上限 2 且瓶内必须至少有 1 个视频。~~ **这条撤销（08-10）**，两个理由都不成立：

- 当反营销闸用是无效的。营销号随手贴一个视频就过关，成本接近零；真正被拦住的是正常用户——Steam 库存页一键成瓶，结果被告知「你还得再去贴个视频」，一键就没了。降门槛是做这件事的全部理由，这条规则和目的直接打架。
- 「游戏 ≤2」的前提是「整瓶都是游戏会让捞瓶体验断」，而这个前提没论证过。游戏卡片本身就是「陌生人在玩什么」的信息，和视频是平等的内容；瓶子总数上限已经是 10 条，再单卡一个 2 没有依据。

真正该管的是行为特征而不是内容配比，见下面第 2 条。

**2. 反营销压力比视频高一个量级。** 视频推荐没什么商业价值，游戏推荐直接对着销量和愿望单。现有的「每 IP 日限 5 瓶」挡不住有动机的人。

需要的规则是：同一 appid 短期内被多设备重复扔入触发降权；新游（发售 30 天内）单独限流；再把现有 `tooConcentrated`（同一频道超过瓶内一半就拒收）平移成「同一发行商」。这三条对准的都是行为特征，不靠内容配比，也不误伤正常用户。必须在上线前做进去，不能等第一批营销号来了再补。

**3. 卡片不能变成导流位。** 游戏卡片只显示封面 + 名字 + 「TA 在玩」，点击跳 Steam 页面。不带「购买」「加愿望单」按钮，不带任何促销字样。这和 BK 对视频画面的红线是同一个精神：产品一旦看起来像导流工具，就没人信它了。

## 五、两项前置验证的结果（2026-08-10 实测）

### 验证一：插件用户扔瓶率——绿灯，而且不用改代码

原计划是给插件加 `from=ext` 标记再等数据。实际不用：**插件捞瓶时早就在传来源了**。`panel.js:75` 的 fish 请求带 `src: "chrome-ext"`，服务端把它写进了访客记录 `v:<device>` 的 metadata `s` 字段（`worker/src/index.js:422`）。瓶子的 metadata 里又有 `d`（扔瓶设备）。两边交叉就是答案，历史数据一直在，一次 KV list 就能算，零改动、零部署、零风险。

拉出来的结果（623 个访客、226 个瓶子）：

| 来源 | 人数 | 扔过瓶 | 扔瓶率 |
|---|---|---|---|
| 插件用户 | 15 | 6 | **40.0%** |
| 网页用户 | 608 | 114 | 18.8% |

**插件用户的扔瓶率是网页用户的 2.1 倍。** 「插件路线能降装瓶门槛」这个假设成立。

但同一份数据翻出一个更扎眼的问题：**装机 82，真正打开过插件面板的只有 15 个，激活率 18%。** 扔瓶必经 popup 面板（`collect.js` 的「装进瓶子」只是暂存到 `pending`，最后仍由 `panel.js` 的 btnThrow 提交），所以这 15 是可信的活跃口径。

也就是说漏斗上真正漏水的地方不是「插件用户不爱扔」——他们爱扔——是**八成的人装完就再没点开过**。

样本量要说清楚：15 人里 6 人扔瓶，40% 的置信区间很宽（约 16%–68%）。方向可信，精确值别当真。

### 验证二：Workers 出口访 Steam——通，但只测了 HKG

部署了一次性探针 `steam-probe`，测完已删除（域名已回 404）。

- 共 16 次探测，13 次全绿：Steam 全部返回 200 + 正确的 `name`，单次延迟 180–350ms
- 3 次 CF `error code 1042`，全部集中在 worker 刚部署后的头几分钟，且都发生在「串行连打 20 个」的重探针版本上。改成一次打 3–10 个后再没出现过
- **没有任何一次是 Steam 返回 429 或 403**——Steam 没有封 Cloudflare Workers 出口

结论：服务端验证这条路能走，比客户端提供元数据更抗伪造，优先走它。

两条局限必须记着：①只测到 HKG 一个 colo，真实用户遍布全球，别的 colo 出口 IP 有没有被 Steam 限流没测过；②总量才几十次，远没摸到 Steam 那个约 200 次/5 分钟的 IP 限流阈值。稳妥做法是服务端验证 + 失败时自动回落到客户端提供的元数据，别把单条路径写死。

## 六、结论与下一步

两个前置条件都是绿灯，但**它们同时也改了「下一件事该做什么」的答案**。

插件用户扔瓶率 40% 说明 A 方案（Steam 一键成瓶）方向对；可它服务的是那 15 个已经会用插件的人。在激活率 18% 没解决之前，把功能做得更强，是给一个只有两成人走进来的房间加装修。

所以顺序应该是：

1. **先修激活**（08-10 已完成，插件 0.1.6 待 BK 提交商店）：`sw.js` 的 `onInstalled` 在首次安装时打开一次 `b.bking.film/?from=ext-install`，网页那边认这个参数、把「怎么用」摆在最上面。这一步不只是提醒——`bridge.js` 会在这一趟把网页的 device 抄给插件，不来这一趟插件就一直是「还没有身份」的状态，扔的瓶子对不上回执。改动不新增任何权限。
2. **再做 Steam**：A（库存页一键成瓶）+ B（商店页装进瓶子）。**不要和第 1 步合并发版**——Steam 必然要新增 host permission，会触发更严的审核，把零权限变化的激活修复绑上去一起冒险不划算。worker 侧和网页侧的改动不需要过审，可以先独立上线。
3. 上线同时把第四节那三条闸做进去：同 appid 跨设备重复扔降权、新游 30 天内单独限流、`tooConcentrated` 平移到发行商。
